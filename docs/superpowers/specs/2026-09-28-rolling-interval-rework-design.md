# 「提醒后计时」重做设计

日期：2026-09-28
状态：**已被 `2026-09-29-rolling-anchor-on-handling-design.md` 取代**（本份零落地；新那份并入了
它的全部内容，并翻掉两处口径：「关闭」算处理、文案改「处理后计时」）

## 1. 背景与目标

用户报的现象：**循环提醒的时间会因为重启应用而变**。原话：

> 循环提醒的时间，如果是提醒后计时，每天第一次计入的时候，记录第一次的提醒时间，然后就不再因为
> 重启而重置…… 例如正常十点弹出，你十点零五点击知道了，那么下一次就是十一点零五弹，然后如果
> 十一点十分点击，那么下次就是十二点十分弹，如果中间重启，下次还是十二点十分，直到这个循环
> 周期结束，到达第二天的，又从时间起始点一小时候开始记录。

即「提醒后计时」的正确语义是 **从「处理」那一刻起算间隔**，而我们现在的实现是"从**触发**那一刻起算"。

## 2. 现状与证据

### 2.1 今天的现场数据（用户 `reminders.json`）

`久坐提醒`：`rolling` / 每 60 分 / 09:00-18:00 / 工作日 / 开了「留记录」。它今天实际弹过的记录：

```
10:02:23  11:02:23  12:02:24  13:02:25  14:02:26      ← 相位 :02（锚 = 今早启动 09:02:23 + 60 分）
```

而文件里存的下一次是 **15:45:31**，`last_fired_at` 是 **None** —— 用户预期是 15:02。

### 2.2 两处都会让节奏漂移的代码

| # | 路径 | 现在做了什么 | 为什么不对 |
| --- | --- | --- | --- |
| 1 | `model.py:378-387` `normalize_on_startup`（重启） | rolling 且已过点 → `next_fire_at = now + 间隔` | 基准被"启动时刻"劫持，相位丢失 |
| 2 | `edit_dialog.py:638-661` + `_COPY_FIELDS:35` + `:682-687`（编辑保存） | 一律 `make_interval(..., now)` 造新对象，再把 `next_fire_at` 复制回原对象、并把 `last_fired_at` 清空 | **只改个文案、甚至什么都不改点保存，排期也被重排** |

### 2.3 复现实测（2026-09-28，隔离数据目录）

照抄 14:45 那次现场跑一遍，数值与真实文件**一字不差**：

```
保存前：next = 2026-09-28 15:02:26  last_fired = 2026-09-28 14:02:26
保存后：next = 2026-09-28 15:45:31  last_fired = None        ← 14:45:31 + 60 分
```

对照：`固定时刻` 模式保存前后 `next` 都是 15:00:00（重算落在同一格）—— 所以**拿固定时刻去试是看不出问题的**，
这也是用户先前"没复现到"的原因。

### 2.4 2026-09-24 的那次裁决（本次要翻案的地方）

`model.py:73-78` 与 `tests/test_model.py:514-517` 都记着：**原设计就是"从处理那一刻起算、没人处理就
一直停着"**，2026-09-24 因为真机表现"过了一小时也没再提醒"（弹窗被压在别的窗口后面没看见 →
这条循环当天永久哑了）而改成"从触发起算"。

**本次不是简单改回去** —— 见 §3 第 2 行：没处理时按"原定时刻 + 间隔"继续往前弹，所以"从处理起算"
回来了，但**不会哑**。

## 3. 「提醒后计时」的新规则

| 情形 | 下一次 = |
| --- | --- |
| 用户**处理**（点「知道了」→ `acknowledge`） | `seek_next_slot(处理时刻 + 间隔)` —— 10:00 弹、10:05 处理 → **11:05**；11:05 弹、11:10 处理 → **12:10** |
| 到点弹了、**没处理** | `seek_next_slot(上次原定时刻 + 间隔)` —— 12:10 没处理 → **13:10** 再弹；一直不处理就一直每格一次（弹窗被新的顶掉、重新置顶） |
| 「稍后 10 分钟」 | **不算处理**，不重锚。snooze 到点触发后按上一行走，所以推迟不会把后续节奏拖着走 |
| 「关闭」（只把弹窗收起来） | **不算处理**，不重锚（现状就是"关闭 ≠ 已处理"，保持一致） |
| **重启**（存着的下一次还没到） | 原样保留，什么都不做 |
| **重启**（存着的下一次已过点，**还是同一天**） | 从存着的那个时刻按间隔往前推到未来第一格 —— 存 12:10、12:30 启动 → **13:10**（不是 13:30） |
| **重启**（存的下一次**不是今天**的） | 回到「**今天的时段起点 + 间隔**」—— 09:00-18:00 每 60 分 → **10:00**（用户规则："到达第二天的，又从时间起始点一小时候开始记录"） |
| 新建 | `seek_next_slot(现在 + 间隔)`（现状不变） |
| **编辑保存** | 排期字段没变（只改文案 / 改「留记录」开关 / 什么都不改）→ **原样保留**；改了间隔 / 时段 / 含不含结束 / 星期 / 日期区间 / 计时方式 → 重排 = `seek_next_slot(保存时刻 + 间隔)`（等于从现在重新开始计时） |

顺延规则（时段外、非允许日、超窗口）**一律沿用现有 `seek_next_slot`**，本次不动。

## 4. 为什么这样就不会回到"永久哑"

老毛病出在"**没处理就一直停在那一刻**"。新规则把"没处理"单独规定成"按原定时刻继续往前推"，
所以：

- 弹窗被别的窗口盖住、用户没看见 → 下一格照常弹（重新置顶），提醒不断线
- 用户处理了 → 从处理时刻重新起算（用户要的节奏）

两条要求同时成立，这是本次设计的核心。

## 5. 代码落点

### 5.1 `reminders/model.py`

| 位置 | 改法 |
| --- | --- |
| `roll_forward()` `:169-173` | rolling 也用 `self.next_fire_at` 当锚 —— 与 fixed 完全相同，两个分支**合并**（`anchor = self.next_fire_at`） |
| `acknowledge()` `:265-281` | **新增**：`kind == "interval"` 且 `interval_mode == "rolling"` 且 `enabled` 时，`next_fire_at = self.seek_next_slot(now + self.interval_delta(), now)` |
| `normalize_on_startup()` `:378-387` | rolling 分支不再用 `now + 间隔` 重锚。三分支：① `next_fire_at > now` → `continue`；② 已过点且 `next_fire_at.date() == now.date()` → `seek_next_slot(next_fire_at + 间隔, now)`；③ 已过点且不是今天 → `seek_next_slot(combine(now.date(), first_slot_time()), now)` |
| `model.py:70-79` 注释 | 重写 rolling 的定义（"从处理起算；没处理按原格继续" + 本次翻案的缘由 + 2026-09-24 那段历史要保留下来当依据） |
| `model.py:355-368` normalize 的 docstring | 同步改（现在写的是"启动那一刻当作一次隐式提醒"） |
| `make_interval()` docstring `:407-408` | "从现在起算一个间隔"仍然对，但补一句"之后由处理驱动" |

`Reminder` **不加新字段** —— `next_fire_at` 本身就是持久化的基准，够用。

### 5.2 `reminders/edit_dialog.py`

保存路径（`on_ok()` 的 `else` 分支，`:681-688`）加一层判断：

```python
if is_new:
    result.append(fresh)
else:
    schedule_kept = base.kind == "interval" and base.interval_mode == "rolling" \
        and _same_schedule(base, fresh)          # 排期字段逐个比
    for f in _COPY_FIELDS:
        if schedule_kept and f in ("next_fire_at",):
            continue                             # 保留原定的下一次，不重排
        setattr(base, f, getattr(fresh, f))
    if not schedule_kept:
        base.last_fired_at = None                # 现在是"从现在重新计时"，清掉旧的触发记录
    base.done = False
    base.snooze_until = None
    base.enabled = True
    result.append(base)
```

`_same_schedule(base, fresh)` 比较的字段（**只有这些算"排期"**）：
`interval_minutes`、`window_start`、`window_end`、`include_end`、
`repeat_mode`、`weekdays`、`date_from`、`date_to`、`interval_mode`。

其余类型（once / daily / fixed）**保持现状**：它们的重算结果只由"设置 + 现在"决定、跟重启无关，
不会漂，没必要动（YAGNI）。

1. `10:00 弹 → 10:05 处理 → 下一次 11:05`
2. 连续两轮：`11:05 弹 → 11:10 处理 → 12:10`
3. 重启不重锚：存 `12:10`、11:30 启动 → 仍是 `12:10`

## 7. 数据影响

用户那条 `久坐提醒` **不用迁移**：

- 现在存的下一次是 `15:45:31`（14:45 那次编辑留下的，今天已过）
- 新规则下下次启动：同一天已过点 → 沿格子往前推 → 今天 `16:45:31`、`17:45:31`…
- 相位 `:45` 会一直保留到用户**处理**一次为止，之后就跟处理时刻走了

要它走"整点格子"（10:00/11:00…）是另一回事：把这条的计时方式改成**「固定时刻」**即可，
不用改代码（属于数据操作，可随时做）。

## 8. 明确不做

- 不改「固定时刻」的任何行为（格子对齐时段起点是它的定义）
- 不动「每天」「单次」的排期与文案
- 不改 `seek_next_slot` 的顺延规则（时段外、非允许日、跨天都沿用）
- 不给 `Reminder` 加新字段
- 不动编辑框里「计时方式」这个二选一本身（两个模式的区别依然成立：
  **fixed = 格子永远对齐时段起点、处理不改变节奏；rolling = 处理时重锚**）
- 不做数据迁移脚本

## 9. 风险 / 待实测

1. **弹窗顶掉时的观感**：没处理时每格都弹一次、旧弹窗被新弹窗覆盖（这是现有的 `close_all()` 行为）。
   长时间不处理会一直弹 —— 这正是 2026-09-24 想要的"不断线"，但**要真机看一眼能不能接受**
2. **处理时刻恰好落在时段结束之后**：`seek_next_slot(处理时刻 + 间隔)` 会顺延到下一个允许日的第一格，
   需要确认符合直觉（预期：符合 —— 时段过了就不该再响）
3. **编辑保存的字段对比**：`_same_schedule` 漏字段会导致"改了不生效"，测试第 7 条要覆盖到每个字段
   （至少覆盖间隔、时段、计时方式这三个最常改的）
4. **`acknowledge` 的调用来源**：弹窗「知道了」（`popup.py:130`）、便签本「标记已读」
   （`main_window.py:777`）两处都会调用 —— 后者对循环便签是否也该算"处理"，实施时确认一次
5. `app.py:74` 的 `entry.acknowledge(now)` 是给**记录条目**（kind=once）用的，不受影响
