# 真实工作日与节假日数据更新 设计

日期：2026-09-22
状态：已实施（2026-09-23 完成，逐条落在 plans/2026-09-22-workdays-holiday-aware.md）

> **实施后更正（2026-09-23）**
>
> 1. §1.1 的「`weekdays=[0,1,2,3,4]` 的自动升级为真实工作日」**已撤销**。`to_dict()` 永远写 `repeat_mode`，所以这个猜法分不出「老文件里的默认值」和「用户刚在界面上明确选的 按星期＋一~五」，后果是用户的选择被一次重启静默改掉（文案变「工作日」、弹窗规则换掉）。现改为只认显式写下的 `repeat_mode`，认不出的（含没有该键的老数据）一律退回「按星期」。代价是老便签里勾一~五 的会退回「周一至周五」—— 本机现有数据里没有这种便签。
> 2. §7 的启动流程加了兜底 `STARTUP_GRACE_TICKS`：若干拍内等不到校时结果就自己开始判定。校时回调是整场判定唯一的启动开关，而它来自后台线程 —— 主线程尚未进入事件循环时跨线程 `root.after` 会抛 `RuntimeError`，回调丢失会导致这一场会话一条提醒都不弹且无可见征兆。
> 3. 打包：Slim spec 的 `excludes` 去掉了 `ssl`/`_ssl`（https 更新需要它们）。
> 4. 措辞更正：§1.1 与 `is_workday()` 注释里的「宁可多弹也别漏」的说法只在「放假的周中」成立；兜底的周一至周五认不出调休上班的周六，那个方向是**漏弹**。README 已按此改口径。

## 1. 背景与目标

「循环」里的「工作日」不是一个独立选项，而是显示层的一个特例：只要勾选的星期恰好是 `[0,1,2,3,4]`，标签就写成「工作日」（`model.py:109-111`）。而真正决定该不该弹窗的 `day_allowed()`（`model.py:170-180`）**只认 `day.weekday() in weekdays`**，完全不知道调休。后果：

- 调休上班的周六（2026 年有 6 天，如 1/4、10/10）**不弹窗**
- 法定放假期间落在周一至周五的那些天（2026 年如 10/1-10/7 整段）**照样弹窗**

本次两件事：

1. 让「工作日」名副其实 —— 按国务院公布的放假安排判断；同时把显示层那个特例的文案改成「周一至周五」，让「勾了一~五」老实说明自己只是周一至周五
2. 让这份放假安排在**不用重新发版**的前提下能持续更新 —— 内置一批 + 联网更新

### 1.1 已与用户确认的决定

| 决定点 | 结论 |
| --- | --- |
| 规则范围 | **只做「跟随法定节假日」**；大小周/轮班表不做（见 §1.2） |
| 首批数据 | 随应用发版内置 2026 年（放假日 33 + 调休上班 6） |
| 数据更新 | 启动时**本地判断**（零成本，每次启动都做）；**只在数据快不够用时才联网**，联网尝试间隔 **7 天**；不做任何手动入口（见 §3.3） |
| 数据来源 | 吃别人维护的公开数据集（**不托管**），多源轮询（见 §3.1） |
| 拉取范围 | 由**当前年份**推导 `{今年-1, 今年, 今年+1}`；空壳年份不算数（见 §3.3） |
| 数据存放 | 三层：用户手写层 > 联网更新层 > 内置层，**拆成不同文件**（见 §2.2） |
| 数据未覆盖的日期 | 回退周一至周五 + 编辑框提示（宁可多弹也别漏） |
| 旧数据迁移 | ~~`weekdays=[0,1,2,3,4]` 的自动升级为真实工作日~~ **已撤销**（见顶部「实施后更正」） |
| 顺带修 | **NTP 校时由同步阻塞改成异步**（现在会卡启动，见 §7） |

### 1.2 规则范围：为什么不做大小周

评估过把「工作日」做成一族可选规则（`workdays_rule = "statutory" \| "big_small"`），也评估过更通用的「可命名作息方案 + 任意轮班周期」。**结论是不做，只做跟随法定**，理由：

1. **大小周必须有一个基准周**。双休周/单休周两周一轮，程序必须知道"从哪一周开始是大周"，差一周就整套错位。能做对的只有"让用户指定基准周"一种办法（靠自然周序号奇偶会与公司实际排班错位，且错位后用户看不出原因）——于是界面必须多出"基准日"这个对普通用户不友好的输入。
2. **大小周与法定节假日的叠加关系因公司而异**：有的跟国家调休，有的自己排班，还会出现"春节放假但不跟调休"的混合。要做得像真的，就得再给一个勾选，规则数与测试面都翻倍。
3. **通用轮班表（三周一轮、上二休一）** 要配一个管理界面，工量再翻一倍，而当前只有"跟随法定"是确定要用到的。

**不做，但用户仍有两条出路**（写进 README）：

- 固定作息的（单休、双休、休周三…）用现有的**「按星期」**勾一~六 就够了，不需要新规则
- 大小周这种**交替**作息，用手写层 JSON 单日覆盖（§2.2）把单休周的那些周六写进 `makeup_workdays`。手工、麻烦，但可行，且不动程序

**若以后真要加规则**，扩展点是现成的：`workdays` 模式下加一个 `workdays_rule` 字段 + 一个分支，`day_allowed()` 仍是唯一判断入口。本次**不预埋任何字段**（不留空实现）。

### 2.2 三层数据与文件

| 层 | 文件 | 谁写 | 覆盖关系 |
| --- | --- | --- | --- |
| 用户手写层 | `%APPDATA%\RemindNotes\holidays.local.json` | **只有用户**，程序永不写 | 优先级最高，永不覆盖 |
| 联网更新层 | `%APPDATA%\RemindNotes\holidays.json` | 程序（联网更新时整体替换） | 覆盖内置层 |
| 内置层 | `reminders/data/holidays.json`（打进 exe） | 发版时 | 保底 |

**为什么拆成两个文件**：联网更新要整体替换自己那份，而"临时给自己加一天"也写在磁盘上 —— 同一份文件的话，下次启动更新就把用户手写的内容静默抹了。拆开之后两层各写各的，谁都不会踩谁。这是个数据丢失 bug 的预防，不是洁癖。

三份用同一套 schema：

```json
{
  "version": 1,
  "source": "国办发明电〔2025〕7号《国务院办公厅关于2026年部分节假日安排的通知》",
  "updated": "2026-09-22",
  "covered_from": "2026-01-01",
  "covered_to": "2026-12-31",
  "holidays": ["2026-01-01", "..."],
  "makeup_workdays": ["2026-01-04", "..."]
}
```

- `holidays` = 放假（不弹窗）；`makeup_workdays` = 调休上班（弹窗）。不在两个列表里的日子按"周一至周五"算 —— **这张表只记异常日，不记全年的每一天**。
- 手写层可以只写自己要动的那几天，`covered_from`/`covered_to`/`source`/`updated` 都可省：

```json
{ "holidays": ["2026-09-23"], "makeup_workdays": ["2026-10-10"] }
```

- 内置层随发版带 2026 那年；后续年份靠联网更新（§3），**不需要重新打包**。

### 2.3 判定顺序

`is_workday(day)` 就是按这个顺序，先命中先返回：

1. 在手写层 `makeup_workdays` → 上班
2. 在手写层 `holidays` → 放假
3. 在联网层 `makeup_workdays` → 上班
4. 在联网层 `holidays` → 放假
5. 在内置层 `makeup_workdays` → 上班
6. 在内置层 `holidays` → 放假
7. 其余 → `weekday() < 5`

手写层排最前，是为了两个方向都能单点覆盖内置数据：

- 想给自己加一天假 → 写进手写层 `holidays`
- 想休掉一个全国调休上班日（如 10-10 自己请年假）→ 写进手写层 `makeup_workdays`

只把"上班"放最前、放假放后面是不够的，两层的"上班/放假"都必须整层优先，否则盖不住下层的调休。

### 2.4 加载与容错

- 三层各自独立解析：**任一层坏掉/缺字段 → 只忽略那一层**，其余照用。用户手抖写坏了 `holidays.local.json`，绝不能连内置的 33 天一起丢。
- 三层全拿不到（只在开发态）→ 进入"无数据"状态：全部按周一至周五判断。
- 一律**不弹错、不崩、不写日志**。解析结果在内存缓存，启动读一次盘。
- 日期格式不合法的条目**单条丢弃**，不牵连同层其它条目。

## 3. 联网更新

### 3.1 数据源（2026-09-22 实测）

| 源 | 实测 | 用途 |
| --- | --- | --- |
| `https://cdn.jsdelivr.net/gh/NateScarlet/holiday-cn@master/{year}.json` | HTTP 200，4843B，1.3s | **首选** |
| `https://raw.githubusercontent.com/NateScarlet/holiday-cn/master/{year}.json` | HTTP 200，2.4s | **兜底**（注意 `github.com` 本机不通，但 `raw.githubusercontent.com` 通） |
| `https://api.apihubs.cn/holiday/get?year={year}` | HTTP 200，9277B | 备选，需额外适配层，本次不用 |
| `https://timor.tech/api/holiday/year/{year}` | HTTP 403 | 排除 |

`holiday-cn` 是第三方维护的公开机器可读数据集（内容源自国务院通知），有 `year` / `days` 字段，**不托管**这条满足了。

### 3.2 格式与语义

数据集条目形如：

```json
{"name": "元旦", "date": "2026-01-01", "isOffDay": true}
```

**`isOffDay: true` 表示"这天放假"**（`isOffDay: false` = 调休上班）。注意这个字段极易读反 —— 起草本设计时第一遍就读反了。所以 §9 必须有测试拿两条已知事实钉死语义：`2026-01-01`（元旦）应为放假、`2026-01-04`（调休）应为上班。

映射到自己那份 schema 时只是分组，不需要复杂适配：

- `isOffDay == true` → `holidays`
- `isOffDay == false` → `makeup_workdays`

### 3.3 时机：按需更新（本地判断 + 7 天尝试节流）

两件事要分开，别混成一件：

**① 判断（纯本地，零网络、零成本）**：`need_update()` = 现有 `covered_to` 为空、**或它距今天不足 45 天**。每次启动都跑一次 —— 因为不联网，跑多少次都无所谓。

**② 联网尝试**：只有 `need_update()` 为真、**且距上次尝试 ≥ 7 天**时才发请求。无论成败都记下这次尝试时间（`prefs.json`），所以不会反复撞。

实际效果：

| 时间 | 行为 |
| --- | --- |
| 2026-09（数据到 2026-12-31，还剩 100 天） | **完全不联网**，启动秒过 |
| 2026-11-17 起（只剩 45 天） | 每 7 天试一次，直到拿到 2027 的数据 |
| 拿到之后（`covered_to` 变 2027-12-31） | 又一次整年不联网 |

- **45 天缓冲是给"国务院 11 月才公布次年安排"留的窗口**：从 11 月中开始试，有 6 周机会；哪年发布晚了也不至于元旦断档（真断了也只是退回周一至周五，不会不弹窗）
- **7 天节流的另一层作用**：年末那几周若一直失败（断网、被墙），也不会每次启动都去撞一次
- 首次安装、数据缺失（`covered_to` 为空）会立刻进更新流程，不被节流挡住

**拉取范围**：由**当前年份** `y` 推导出的 `{y-1, y, y+1}` 三个年份各拉一次（多源逐个试），合并后写入联网层。为什么带上去年：判定本身只朝前看，缺去年在行为上无害；但跨年后那几天、以及"电脑关机很久后重启"时 `seek_next_slot` 会从过去的日期开始走，手上有去年的数据就不用退回周一至五猜。多一个 GET，只在更新窗口里发生，成本可以忽略。

**次年的文件是个"空壳"，不是 404**（2026-09-22 实测）：`2027.json` 返回 **HTTP 200 但 `days` 为空**，`year` 字段已经是 2027。所以**"拿到文件"不等于"有数据"** —— 见 §3.4 的校验规则，空 `days` 必须按"该年没有数据"处理，否则 `covered_to` 会跳到 2027-12-31，编辑框就会显示一句骗人的"数据到 2027-12-31"（正是 `main_window.py:573-583` 那条原则所反对的）。空壳会让 `need_update()` 继续为真，下一次窗口期接着试 —— 这正是我们要的：等它填上 `days`。

`covered_to` 取**有非空数据的**最大年份的 12-31。写盘时只保留拉取的那三年，更早的年份丢掉。

### 3.4 校验与落盘

1. 解析 HTTP 响应为 JSON，按 §3.2 映射成自家 schema
2. **年份一致性校验**（用户提出，防拿错年份）：
   - 数据里的 `year` 字段必须**等于请求的年份** —— 不等就整份丢弃（防镜像串档、CDN 缓存串号、文件名拼错）。实测该字段确实存在且正确（2025/2026/2027 各自对得上）
   - 每条日期的年份必须**等于该份数据的 `year`** —— 不等就**单条丢弃**（防数据集内部串档）
   - 该份数据的 `days` 为空 → **该年没有数据**，不算成功、不参与 `covered_to`（§3.3 那个空壳坑）
3. 合并后，**有数据的最大年份必须 ≥ 今年**，否则拒绝覆盖（既有"拒绝倒退"规则的加强版：防镜像返回旧一年的数据把好数据换掉）
4. 其余格式校验：必需字段存在且类型正确、日期是合法 ISO 日期
5. **先写临时文件 → 校验通过 → 原子替换**（`os.replace`）。任何一步失败都保留现有文件不动
6. 更新内存缓存（见 §4）—— 否则得等下次启动才生效

### 3.5 失败处理

断网、CDN 挂了、公司封了域名、数据集改格式、次年文件还没发布 —— 全部走同一条路：**保持现有数据不变**，程序照常。手写层与内置层都在下面兜着，最坏情况就是"工作日退化成周一至周五"，绝不出现"因为更新失败所以提醒不弹窗了"。

### 3.6 形状可以照抄的部分

- 多源逐个试、全失败返回 `None`（`clock.py:60-75`）
- 后台线程 + 回调，并在注释里写明"回调在后台线程，调用方需自己 `root.after(0)` 回主线程"（`clock.py:96-107`）—— `sync_async` 目前**没有任何调用者**，本次它会被两处用上：校时自己（§7）与节假日更新
- 模块级缓存 + `threading.Lock`（`clock.py:21-24`）：后台线程写、主线程读，靠锁保证不会读到半截数据
- 只有真成功才敢对外声称"已更新"（`main_window.py:573-583` 那条"没校准上就不写「网络校准」"的原则）

### 3.7 隐私、离线开关与行为变化

- 只 GET **硬编码的地址模板**（两个域名）+ 由当前年推导出的三个年份，不上传任何东西；URL 不接受用户输入（不把它做成任意 URL 下载器）
- 联网时机：**平时启动根本不联网** —— 只有 `need_update()` 为真（`covered_to` 空了或不足 45 天）且距上次尝试 ≥7 天，才会去拉（§3.3），而且没有手动入口。应用本来每次启动就静默连 NTP 校时，所以联网姿态没有变差，反而更少（§7）
- 更新完就断网照常使用 —— 数据落在磁盘上，运行时不需要网络
- **离线开关**：新增环境变量 `REMINDNOTES_OFFLINE=1`，`clock.sync_async` 与节假日更新都尊重它，置上就都不联网。**不做成界面开关**（本来就没为 NTP 做过），它存在的主要目的是让测试套绝对离线（§9）

## 4. `reminders/holidays.py`（新文件）

对外：

- `is_workday(day: date) -> bool` —— 按 §2.3 的 7 步判定，末步是 `weekday() < 5`。**不把"是否有数据覆盖"泄漏给调用方**：覆盖范围内外的兜底结果相同（都是周一至周五），调用方不需要知道

- `need_update() -> bool`、`fetch_from_network(timeout) -> dict | None`、`update() -> bool`、`update_async(on_done)` —— 见 §3（没有 `force` 参数：没有手动入口，不需要绕过节流）

## 7. 顺带：把 NTP 校时改成异步

**现状的卡顿来源**：`app.py:23-27` 在 `App.__init__` 里同步阻塞地 `clock.sync(timeout=1.5)`，而 `fetch_beijing_time` 对 **3 个源各给一次 timeout**（`clock.py:60-75`）—— 所以断网时最坏要白等 **3 × 1.5 = 4.5 秒**，表现就是"双击图标后好几秒没反应"。

**改法**（用现有的接缝，不新造流程）：

- `App.__init__`：去掉阻塞校时；**并把 `scheduler.startup()` 也移出去**（`app.py:36-37`）
- `App.setup()`（`app.py:127`）：起 `clock.sync_async(...)`，**且不在这里起 tick 循环**（现在是 `app.py:145` 的 `root.after(TICK_MS, self._tick)`）
- 校时回调经 `root.after(0, ...)` 回主线程之后，才依次：① 跑 `scheduler.startup()`（normalize）② 起 tick 循环 ③ 刷一次界面
- `sync_async` 的线程是 daemon、timeout 有限，**成功与失败都会回调**，所以这三步一定会执行，不会出现"永远不 tick"

**为什么 normalize 必须延后到校时出结果之后**：`normalize_on_startup()` 会把"已经过点的 daily"滚到下一次（`scheduler.py:16-18`）。若先用偏快的本机时钟跑，一个 09:00 的 daily 在真实 08:50 就可能被滚到明天，**校准回来也没法回滚**，代价是漏弹一次。延后之后，normalize 拿到的一定是最终确定的 now（校准成功用校准值，失败/超时用本机值）。这是本次唯一需要小心的地方。

**代价**：校时出结果之前不 tick，最坏 4.5 秒（断网）内到点的提醒会晚几秒。比"启动卡 4.5 秒"值得。

**不用额外处理的部分**：`tick()` 每秒重读 `clock.now()`（`scheduler.py:25`），校准落地后判定自动用新时间；底部时间文字由 `_tick_clock()` 每秒刷新（`main_window.py:602-607`），会自己从「本地时间」变成「北京时间 · 网络校准」，不需要另外通知界面。

**顺带**：`clock.sync_async` 目前没有任何调用者，本次是它的第一个真实用途。

## 10. 明确不做

- 不做大小周 / 通用轮班表（§1.2 有完整理由与逃生出口），不预埋 `workdays_rule`
- 不做「节假日设置」窗口：加一天就是改手写层那个 JSON
- **不做任何手动更新入口**：不加托盘菜单项、不做按钮，更新全自动（所以那五项菜单的断言也保持不动）
- 不做**整体替换**语义：手写层只在其它层之上叠加与覆盖单日
- **不做界面上的联网开关**：本来就没为 NTP 做过；只有测试用的环境变量 `REMINDNOTES_OFFLINE=1`
- 主窗口不给受影响的提醒打「数据过期」标记 —— 数据没跟上时它会静默按周一至五跑，只有编辑框那行小字能看见
- 不自建数据托管（用户明确要求不托管）
- 不补 2026 年以前的历史年份（提醒只朝前算，用不到）

## 11. 风险

- **数据准确性**：本设计里"抄错一天"的风险已基本消除 —— §2.1 的表与第三方数据集逐条比对差异为 0。剩下的是**第三方数据源本身出错或改格式**，由 §3.5 的"失败即保持现状"和内置层兜住。
- **第三方源停更**：`holiday-cn` 若某年不再更新，联网更新会失败 → 退化成"数据停在最后拿到的一年 + 周一至周五兜底"，程序仍可用，只是工作日不再准。届时要换源（§3.1 的备选）或改为自建，属于已知的、可接受的依赖。
- **联网层写盘覆盖手写层**是本次特意拆文件避免的 bug；实现时若图省事写成同一个文件，就会静默抹掉用户手写的例外日。
- 迁移是单向的（读完就变 `workdays`，不会再退回 `weekdays`）。旧那条提醒的行为会变——这正是用户要的结果。
- **校时异步化引入一个启动窗口**（§7）：校时出结果之前不 tick，最坏 4.5 秒（断网）。落在这几秒内到点的提醒会晚几秒弹。缓解手段是把 `sync` 的 timeout 调小（更短的无 tick 窗口，代价是慢网络下校不上），实施时按 §7 的 1.5s 起步，觉得不够再看。
