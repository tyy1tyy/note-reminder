# 「处理后计时」——rolling 锚点收到处理时刻（合并 2026-09-28 那份）

状态：设计已确认，实施中
取代：`2026-09-28-rolling-interval-rework-design.md`（那份也是"设计已确认、待实施"，但零落地；

## 1. 起因

用户看列表时发现：`久坐提醒` 是「提醒后计时」，自己 14:0X 才点「知道了」，而存的下一次是 `15:00:02`
（= 弹出时刻 14:00:02 + 60 分）。也就是说 —— **点没点、几点点，都不影响节奏**，这与"提醒后计时"
的字面读法（处理之后再计时）相反。

翻代码确认现状：`acknowledge()` 对循环只收 snooze、完全不碰排期（`model.py:274-281`），
弹窗「关闭」也不改排期（`popup.py:124-127`），`roll_forward()` 的 rolling 分支锚在**触发**那一刻
（`model.py:169-173`）。这是 2026-09-24 的裁决（原设计"从处理起算、没人处理就停着"导致弹窗被压住
没看见时这条循环当天永久哑掉）。

同时发现 2026-09-28 已有一份针对同一件事的 spec（动机是"循环时间会因重启而变"），同样未落地，
而且覆盖范围更宽：重启相位、编辑保存重排。故本次合并实施。

## 2. 最终规则（rolling = 「处理后计时」）

一句话：**下一次 = 「这一格被处理的时刻 + 间隔」；一直没处理就用「这一格触发时刻 + 间隔」。**

| 情形 | 下一次 |
| --- | --- |
| 弹窗上点「知道了」或「关闭」 | `处理时刻 + 间隔`（14:00 弹、14:05 点 → **15:05**）|
| 到点弹了、没人碰（压在其他窗口后面/没看见） | `触发时刻 + 间隔`，到点照弹、把旧弹窗顶掉（**不断线**，现状不变）|
| 「稍后 10 分钟」 | **不算处理**，不重锚；snooze 到点再弹，在那一张上按上面的规则算 |
| 主窗口「标记已读」 | **不算处理**，不动排期（它是事后清列表，不代表看到了那张弹窗）|
| 重启，存的下次还没到 | 原样保留 |
| 重启，存的下次已过点且**同一天** | 从存的时刻按间隔往前推到未来第一格（存 12:10、12:30 启动 → **13:10**，不是 13:30）|
| 重启，存的下次**不是今天** | 回到「**今天的时段起点 + 间隔**」（09:00-18:00 每 60 分 → **10:00**）|
| 编辑保存，排期字段没变（只改文案 / 改「留记录」） | `next_fire_at` 原样保留，**不清** `last_fired_at` |
| 编辑保存，排期字段变了（间隔/时段/含结束/星期/日期区间/计时方式） | 重排 = 保存时刻 + 间隔（等于"从现在重新计时"），清 `last_fired_at` |
| 新建 | `现在 + 间隔`（现状不变）|

顺延（时段外、非允许日、跨天）**一律沿用现有 `seek_next_slot`**，本次不动。
「固定时刻」的行为**一点不改**：它的格子永远对齐时段起点，处理不改变节奏。

## 3. 为什么不会退回"永久哑"

老毛病出在"没处理就一直停在那一刻"。新规则把"没处理"单独规定成"按触发时刻继续往前推"，
所以：没看见 → 下一格照常弹（重新置顶）；处理了 → 从处理时刻重新起算。两条要求同时成立。

## 4. 代码落点

| 位置 | 改法 |

## 6. 相对 2026-09-28 那份的两处翻案

1. **「关闭」算处理**（那份写的是不算，理由是"与单次便签的『关闭 ≠ 已处理』保持一致"）。
   2026-09-29 用户裁决：算 —— 弹窗上两个按钮对循环便签等价。
   代价：失去"只把纸收起、保持原节奏"这个用法（单次便签上「关闭」仍然 ≠ 已处理）。
2. **文案改成「处理后计时」**（那份明确写"不动二选一本身"）。新语义下旧词的"提醒后"会被读成
   "弹出后"，与行为相反。新词等长，列宽零改动。

## 7. 数据影响

现有 `久坐提醒` **不用迁移**。它今天已按旧规则排到 `15:00:02`，改完之后：
如果用户不动它 → 15:00:02 照弹、下一格 16:00:02（相位 :02 保留）；
用户在弹窗上点一下 → 从那一刻重新起算（变成 `:0X` 相位）。
想让它走整点格子，把计时方式改成「固定时刻」即可，不用改代码。

## 8. 明确不做

- 不改「固定时刻」的任何行为
- 不动「每天」「单次」的排期与文案
- 不改 `seek_next_slot` 的顺延规则
- 不给 `Reminder` 加新字段
- 不改主窗口「标记已读」的语义（仍然不算处理）
- 不做数据迁移脚本

## 9. 风险 / 待实测

1. **弹窗顶掉时的观感**：没处理时每格都弹一次、旧的被新的覆盖（现有 `close_all()` 行为）。
   长时间不处理会一直弹 —— 这正是"不断线"的代价，真机看一眼能否接受
2. **「关闭」语义变化**：单次便签上「关闭」仍 ≠ 已处理，循环上却算处理，这个不对称要在真机上确认体感
3. **编辑保存的字段对比**：`_same_schedule` 漏字段 → 改了不生效，测试第 7 条要逐个覆盖
4. **相位漂移消失**：`roll_forward` 合并后，rolling 的格子不再逐格 +1 秒；列表里看不到具体时刻，
   只能靠真机连点两格确认（或看 `reminders.json` 的 `next_fire_at`）
